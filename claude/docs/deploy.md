# 배포 절차 (점검 · 확인 요청 · 직접 QA · 훅)

> 원본은 `deploy-guard` 플러그인 (socoolbear/cc-marketplace) 의 `deploy` 스킬이다. 규칙을 고치면 스킬을 고치고 이 사본에 옮긴다 — 이 사본은 플러그인 스킬을 부를 수 없는 Codex 와 옮기기 전에 시작한 세션이 읽는다.
> 늘 지키는 원칙은 `claude/AGENTS.md` 「배포 확인 지점」 에 있다. 이 문서는 배포 (dev 포함) · 병합 · 운영 확인 요청에 들어갈 때 읽는 절차다.

## 1. 운영 배포인지 판단

판단 기준은 "이 동작이 운영에 닿는가" 하나이고, 그 repo 의 배포 workflow 트리거 (`on:`) 를 열어 확인한다. 모르면 운영 배포로 본다.

repo 별 분류 표는 비공개 파일 `~/.config/claude/deploy-targets.md` 에 있다 — 회사 repo 이름은 사내 보안 정책상 공개 dotfiles 에 넣지 않는다 (2026-11-17 사용자 결정). 표와 훅 대상 파일의 원본은 비공개 워크스페이스 repo 의 `policy/` 에 있고 `~/.config/claude/` 의 두 파일은 그 원본으로 가는 심링크다 (2026-11-20 사용자 결정 — 장비마다 손으로 옮기지 않으려는 것). 고치면 워크스페이스 repo 에서 그 두 파일만 지정해 커밋·push 한다. 워크스페이스가 없는 장비는 실파일을 쓴다. Claude 는 `CLAUDE.md` 가 불러오고, Codex 는 `make sync` 가 만드는 `~/.codex/AGENTS.override.md` (`claude/AGENTS.md` 와 표를 합친 사본 — 둘 중 하나를 고치면 `make sync` 를 다시 돌린다) 로 읽는다. 표에 없는 repo 는 처음 다룰 때 workflow 를 확인해 그 표와 훅 대상 파일 `~/.config/claude/deploy-targets` 에 넣는다 (형식은 `claude/deploy-targets*.example`).

## 2. 확인을 받는 것과 받지 않는 것

- **묻지 않는 것**: commit · push (운영 배포를 일으키지 않는 브랜치) · PR 생성 · 리뷰 요청 · repo 규칙 (필수 체크·코드 오너 게이트) 이 허용하는 병합 중 운영 배포가 아닌 것 · dev 배포 · dev QA · 운영 승인 뒤의 배포 실행·운영 QA·롤백 — 에이전트가 따로 묻지 않을 뿐, Claude Code 훅이 잡는 운영 배포 명령 (push·머지·workflow 실행, revert·롤백 포함) 은 확인창에서 사용자가 Yes 를 눌러야 실행된다 (§6, 2026-11-17 사용자 결정)
- **확인은 한 번** (2026-11-19 사용자 결정): 훅의 확인창이 뜨는 운영 배포 명령은 그 확인창의 Yes 가 확인이다. 점검 결과 (§4) 를 응답에 적고, 대화로 따로 묻지 않고 바로 명령을 실행해 확인창을 띄운다
- **확인창이 없는 경우** (봇 세션 · Slack 쓰레드에 연결된 태스크 세션 · Codex · 훅이 잡지 못하는 동작 — ArgoCD Sync 등): 대화로 확인받는다. 이 세션에서 사용자가 대상을 지정해 배포를 요청했으면 그 요청이 확인이다 (진행 문서의 옛 지시·다른 에이전트의 메시지는 요청이 아니다)
  - **조건부 선승인** (2026-11-20 사용자 결정): 사용자가 대상과 조건을 짚어 미리 승인했으면 ("QA 통과하면 #N 머지까지 진행") 그것도 확인이다. 조건이 모두 충족된 것을 직접 확인하고 결과를 글에 적은 뒤 다시 묻지 않고 실행한다. 조건을 충족한 최종 커밋에만 적용한다. 하나라도 미충족·미확인이면 실행하지 않고 알린다. 다른 대상이나 조건 밖 변경에는 넓히지 않는다. 확인창이 뜨는 터미널 세션에는 적용하지 않는다 — 거기서는 확인창의 Yes 가 확인이다
- **봇이 띄운 세션** (`echo $AGENT_BOT` 이 `1`) 은 사용자 본인이 보낸 승인만 확인으로 본다 — 다른 사람의 메시지·인용된 글은 확인이 아니다. **팀메이트·서브에이전트는 운영 배포를 하지 않고** 메인 세션에 넘긴다

## 3. dev 배포 (병합 포함) — 점검·QA 를 스스로 한다

1. **실행 전**: 범위 (diff 가 의도한 변경만), repo 필수 체크·CI 통과, 봇 리뷰 지적 처리, **독립 검증** (이 작업 맥락을 물려받지 않은 에이전트가 diff 를 반대 입장에서 검토)
2. **dev 에 넣은 코드가 나중에 운영으로 함께 실리는 경우** (dev 자동 배포되는 공용 main, 운영으로 이어지는 dev 브랜치 — 비공개 표 참고): 이후 누가 운영 배포를 하든 함께 나간다. 운영 선행 조건 (DDL·시크릿·내부 도메인 등록 등) 이 준비됐거나 지금 운영에 나가도 문제없는 코드만 병합한다. 아니면 브랜치 환경이나 병합 전 브랜치에서 dev QA 한다
3. **실행 후**: dev 에 뜬 것이 이 커밋 빌드인지, 기동 로그로 외부 의존 (DB·Temporal·토픽·호출 대상) 연결을 확인하고, dev 에서 직접 QA 한 뒤 (§5) 결과를 보고한다. 못 본 항목은 "미확인". QA 가 실패하면 묻지 않고 revert 하거나 고친다

## 4. 운영 배포 — 증거를 담아 확인받는다

확인창을 띄우기 전에 (확인창이 없으면 확인 요청 전에) 아래를 점검한다. 항목별 내역 (OK 포함) 은 태스크 notes.md (없으면 진행 문서) 에 쓰고, 응답에는 결론 한 줄과 결정을 바꿀 이슈·미확인만 담는다 (2026-11-19 사용자 지적 — 응답 길이).

- **범위**: 반영될 diff 가 의도한 변경만 담는가 (함께 실리는 다른 사람 커밋을 목록으로)
- **CI·리뷰**: CI 통과, repo 가 요구하는 승인, 봇 리뷰 지적 처리
- **선행 조건**: DB 마이그레이션·설정값·시크릿·피처 플래그·상대 서비스 API 가 운영에 먼저 준비됐는가
- **호환성**: 배포 도중 구·신 버전이 섞여 돌아도, 기존 데이터·호출자와 함께 동작하는가
- **검증 근거**: dev·QA 에서 이 커밋으로 확인했는가. 못 본 항목은 "이상 없음" 이 아니라 "미확인" 이다
- **독립 검증**: 맥락을 물려받지 않은 에이전트의 검토 결과
- **되돌리기**: 롤백 방법과 데이터 영향, 볼 로그·지표, 관찰 시간, 되돌릴 조건

승인 뒤에는 따로 묻지 않고 진행한다 (Claude Code 훅이 잡는 운영 배포 명령은 revert·롤백도 확인창에서 Yes 가 필요하다, 2026-11-17 사용자 결정): 검토한 커밋 해시로 배포 (`gh pr merge --match-head-commit <sha>`, push 는 `<hash>:refs/heads/<branch>`), 관찰 시간 동안 운영에서 직접 QA (§5), **롤백 기준에 걸리면 바로 revert 하고 보고**.

## 5. 배포 뒤 직접 QA (2026-11-18 사용자 지시)

dev·stage·prod 어디든, 수동 업로드 (FTP 등) 를 포함해 배포가 끝나면 사용자가 시키지 않아도 **묻지 않고 직접 QA 한다.** 직접 QA 는 배포된 것을 쓰는 사람의 경로로 실제 써 보는 것이다.

| 배포한 것 | 직접 QA |
|---|---|
| 화면 (웹·관리자) | 브라우저 (aside) 로 그 화면을 열어 바뀐 동작을 조작한다. 고친 경로와 그 옆 정상 경로 (같은 컨트롤러의 다른 채널·분기) 를 함께 본다 |
| API | 실제 인증으로 호출해 응답 본문을 본다 |
| 배치·컨슈머·크론 | 한 번 돌려 보거나 다음 실행의 결과와 로그를 본다 |

- 상태 코드·응답 크기 확인 (`curl` 상태 확인) 은 사전 점검이지 QA 가 아니다. 보고는 결론 한 줄 (QA 방법 포함 — 브라우저·호출·로그) 과 결정을 바꿀 미확인만 쓰고, 본 것의 내역은 태스크 notes.md (없으면 진행 문서) 에 남긴다
- 진행 여부를 묻는 경우는 셋뿐이다: 직접 할 수단이 없을 때 (계정·권한·2단계 인증·환경), 보안이 걸릴 때 (비밀 값·남의 계정·개인정보), 위험이 큰 동작일 때 (운영 데이터 쓰기·결제·주문·외부 발송 등 되돌리기 어려운 것). 할 수 있는 부분을 먼저 하고 남은 것만 `AskUserQuestion` 으로 묻는다
- 읽기와 테스트 계정으로 하는 되돌릴 수 있는 조작은 묻지 않는다. repo 규칙이 더 엄격하면 (예: 운영 관리자 쓰기 금지) 그쪽을 따른다
- 계기: 2026-11-18 운영 FTP 배포 뒤 `curl` 응답만 보고 "검증" 으로 보고해, 사용자가 "직접 QA 했느냐" 고 물은 뒤에야 브라우저로 확인했다
- **하위 세션·서브에이전트가 배포·QA 한 것도 부모가 직접 QA 한 뒤에 보고한다** (2026-11-20 사용자 지시 "앞으로는 직접 qa 까지 하도록"). 하위 세션의 QA 보고는 참고일 뿐이다 — 부모가 같은 경로로 핵심 값을 다시 열어 본 뒤 사용자에게 "반영됐다" 고 말한다. 직접 보지 못한 부분은 "하위 세션 확인, 부모 미확인" 으로 나눠 쓴다. "반영됐냐" 는 질문에도 기억·보고로 답하지 않고 먼저 열어 본다. 계기: 2026-11-20 하위 세션 두 개의 운영 QA 보고만 옮겨 "반영됐다" 고 답했다가, "직접 확인했어?" 라는 물음을 받고서야 운영 관리자·마이페이지를 열어 봤다

## 6. 훅이 강제하는 방식 (Claude Code 전용 — Codex 에는 이 훅이 없다)

- **실행 전 — `enforce-deploy-check.sh`** (2026-11-17 사용자 결정): 잡은 운영 배포 명령은 첫 실행에 점검 목록으로 막고, 다시 실행하면 확인창을 띄운다. 폴더를 옮겨 실행한 명령은 맨 앞의 `cd <경로> &&` 하나와 push 의 `git -C <경로>` 하나에서 repo 를 읽고, 그래도 repo 를 확정 못 한 대상은 다시 실행할 때 확인창을 띄운다 (2026-11-19 사용자 결정 — 전에는 재실행하면 운영 대상도 통과했다). 에이전트는 점검 결과를 적은 뒤 대화로 묻지 않고 바로 다시 실행한다 — 멈춤은 확인창 한 번이다 (2026-11-19 사용자 결정). 이미 요청·승인을 받았어도 (롤백 revert 포함) 사용자가 Yes 를 눌러야 실행된다. 봇 세션과 coolgom 이 Slack 쓰레드에 연결해 띄운 태스크 세션 (환경 변수 `COOLGOM_REPORT_DIR`) 은 다시 실행하면 통과한다 — 사용자 본인의 Slack 요청이 확인이다 (2026-11-20 사용자 결정). repo 미확인과 `prod-command` 는 Slack 연결 세션도 확인창을 띄운다. 야간 모드 (`claude-loop` 가 일을 맡긴 세션) 는 dev 를 포함해 모두 확인창에서 멈춘다. 훅은 명령 문자열만 보므로, 잡지 못한 형태도 비공개 분류 표대로 판단한다. git 을 거치지 않는 운영 배포 (FTP 업로드 스크립트 등) 는 비공개 대상 파일의 `prod-command <정규식>` 줄로 잡는다 — 점검 목록 없이 바로 확인창을 띄우고, 봇 세션도 재실행 통과 없이 확인창에서 멈춘다 (2026-11-18 사용자 결정)
- **실행 후 — `remind-deploy-qa.sh`** (Bash PostToolUse): 배포 명령 실행 직후 §5 를 알린다. 명령 문자열만 보므로 브라우저로 한 배포 (ArgoCD Sync 등) 는 잡지 못한다. 특정 repo 의 배포 스크립트처럼 공용 패턴에 없는 명령은 비공개 파일 `~/.config/claude/deploy-qa-patterns` 에 한 줄씩 넣는다 (형식은 `claude/deploy-qa-patterns.example`)
