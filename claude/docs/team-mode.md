# 팀 모드 편성/해산 가이드

> `~/.claude/AGENTS.md` 워크플로우 규칙 8의 상세. 팀메이트를 띄우기 전에 이 문서를 먼저 참조할 것.
> 아래 동작 사실은 Claude Code **2.1.220** 기준으로 확인한 것이다. 버전이 크게 오르면 재확인할 것.

팀 모드는 상시 켜두지 않는다. 필요한 세션에서만 켠다 (꺼져 있으면 팀 기능 자체가 없다):

```bash
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude
```

## 0. 용어

- **팀메이트 (teammate)**: `Agent` 도구에 **`name` 파라미터**를 주면 뜨는 에이전트. 분할 창에서 독립적으로 돌고,
  `SendMessage` 로 서로 대화할 수 있으며, 명단 (roster) 에 등록된다.
- **서브에이전트 (subagent)**: `name` 없이 띄우는 에이전트. 한 번 던지고 결과만 돌려받는다.

핵심 차이는 **명단에 남는가** 다. 서브에이전트는 끝나면 사라지지만, 팀메이트는 명시적으로 해산시켜야 사라진다.

## 1. 팀 vs 서브에이전트 — 어느 쪽을 쓸 것인가

**팀**을 쓴다:
- 병렬 축이 2개 이상이고 (저장소별 / 레이어별 / 관점별),
- 중간에 서로 질문·재지시가 오갈 수 있고,
- 각자 컨텍스트가 커서 메인 창에 다 담기 곤란할 때.

**서브에이전트**를 쓴다:
- 한 번 던지고 결과만 받으면 되는 일,
- **그리고 격리가 필요한 모든 파일 수정 작업.**

> **팀메이트는 worktree 격리를 받을 수 없다.**
> `Agent` 에 `name` 과 `isolation` (또는 `cwd`) 을 같이 주면 팀메이트 분기를 타지 않고
> **조용히 일반 서브에이전트로 떨어진다.** 에러가 나지 않으므로 눈치채기 어렵다.

따라서 파일을 고치는 병렬 작업은 이렇게 갈린다:

| 상황 | 선택 |
|---|---|
| 각자 건드릴 파일이 명확히 나뉜다 | 팀메이트 가능 (소유권 분리 필수) |
| 같은 파일을 여러 명이 건드린다 / 격리가 필요하다 | **서브에이전트 + `isolation: "worktree"`** |
| 마이그레이션·일괄 치환처럼 충돌이 불가피하다 | **서브에이전트 + `isolation: "worktree"`** |

## 2. 편성 원칙

1. **인원 = 병렬 축의 개수.** 2~5명. 축이 1개면 팀을 쓰지 않는다 (서브에이전트로 충분하다).
2. **쓰기 작업은 파일 소유권이 겹치지 않게 자른다.** 못 자르면 1명으로 줄이거나 §1 로 돌아간다.
3. **모델**: 기본적으로 지정하지 않는다 — 리드는 세션 모델 (`/model`), 팀메이트는 `/config` 의
   Default teammate model (미설정 시 리드 세션 모델) 을 따른다.
   예외는 두 가지: 조사·수집용 읽기 전용 스카우트는 `sonnet` 지정 가능 (§3), 기계적 작업의 경량 위임은 §5.
4. **읽기 전용 팀메이트**는 `agentType: Explore` + 프롬프트에 "읽기 전용, 파일을 절대 수정하지 말 것" 을 명시한다.
5. **스폰 프롬프트에 반드시 담을 것**:
   - 담당 범위 (다른 팀메이트와 겹치지 않게)
   - 저장소·디렉토리 **절대경로**
   - 출력 형식 (표 위주 / 코드 전문 붙여넣기 금지 등)
   - 모든 주장에 `파일:라인` 근거 요구
   - 하지 말 것 (수정 금지, 커밋 금지 등)
   - 확인 못 한 것은 "미확인" 으로 남기라는 지시

이름은 역할이 드러나게 짓는다 (`list-domain-scout`, `contract-critic`). 나중에 `TaskStop` · `SendMessage` 의 인자가 된다.

## 3. 역할 카탈로그

> **예시일 뿐이다.** 병렬 축이 다르면 이 표를 무시하고 §2 원칙으로 직접 편성할 것.

| 작업 유형 | 예시 편성 | 리드 역할 |
|---|---|---|
| 조사·현황 파악 | `*-scout` ×2~4 (`Explore`, `sonnet`, 읽기 전용) | 축 분할 → 결과 종합 |
| 설계·방안 비교 | `*-proposer` ×2~3, 각자 **다른 전제**를 부여 | 심판 + 좋은 부분 병합 |
| 구현 | `*-impl` ×1~3, 파일 소유권 분리 (§1 조건 충족 시) | 통합 + 빌드·테스트 |
| 검증·리뷰 | `*-critic` ×2~3, 관점 분리 | 역할 부여 방법은 `@docs/workflow.md` §2 참조 |

## 4. 해산 규약

1. 산출물을 받아 **종합이 끝난 즉시** `TaskStop(task_id: "<이름>")` 으로 정리한다.
2. 남기려면 **다음에 쓸 용도를 한 줄로 댈 수 있어야 한다.** "혹시 몰라서" 는 사유가 아니다.
3. 추가 질문이 필요하면 **새로 띄우지 말고** `SendMessage({to: "<이름>"})` 로 이어 쓴다 —
   컨텍스트가 유지되므로 재조사 비용이 들지 않는다.
4. 사용자에게 최종 보고할 때 남긴 팀메이트가 있으면, **왜 남겼는지 함께 말한다.**

세션을 끝내면 Claude Code 가 팀 디렉토리와 창을 정리하므로 영구 누수는 아니다.
하지만 세션이 도는 동안에는 분할 창을 점유하고, 리드 컨텍스트에 `team_context` 잡음을 계속 흘린다.

## 5. 경량 서브에이전트 위임과 plan approval

위임 대상·기준·절차는 `@docs/workflow.md` §3-1 에 있다. **그 규칙은 팀 모드와 무관하게 항상 적용되고**,
팀메이트도 리드와 똑같이 따른다 — 판단·설계·리뷰는 직접 하고, 스코프가 확정된 구현은 `impl-dev`,
테스트·빌드 실행은 `qa-runner` 에 넘긴다.

팀 모드에서만 다른 점은 아래 둘뿐이다.

- **제약**: 팀메이트의 서브에이전트는 **foreground 로만** 돈다 (background 스폰은 에러).
  병렬 코딩이 필요하면 편성 단계에서 축을 나눌 것.
- **검증**: 테스트 실행은 `qa-runner` 에 돌려도 되지만, 결과 판단과 리드 보고는 팀메이트가 한다.

리드가 팀메이트의 플랜을 승인 (plan approval) 할 때 기준:

- 테스트 커버리지 계획이 없는 플랜은 반려
- 롤백 경로가 명시되지 않은 결제 관련 플랜은 반려
- 스코프 밖 파일 수정이 포함된 플랜은 반려

## 6. 정리 훅

`claude/scripts/team-cleanup-check.sh` 가 `Stop` 훅으로 등록되어 있다.
리드의 턴이 끝날 때 **자기 턴을 마치고 (`isActive: false`) 10분 이상 지난 팀메이트**가 명단에 남아 있으면
정리하라는 메시지를 1회 주입한다.

훅이 침묵하는 경우 (전부 의도된 것):
- 팀 리드 세션이 아닐 때 / 팀을 안 쓸 때
- 계획 모드일 때 (`TaskStop` 을 실행할 수 없으므로)
- 백그라운드 작업이 아직 돌 때
- 팀메이트가 부팅 중이거나 작업 중일 때
- 같은 명단으로 이미 알린 뒤

**아직 결과를 기다리는 중이거나 계획 승인 대기 중이라면 이 메시지는 무시하고 하던 일을 계속하면 된다.**

발동 이력은 아래에서 확인한다:

```bash
cat "${TMPDIR:-/tmp}"/claude-team-cleanup/fired.log
```

오발동이 잦으면 스크립트의 `GRACE_SEC` 를 올리거나, `claude/settings.json` 의 `Stop` 항목만 빼면 즉시 무력화된다.
