# 용어·설명 규칙

> `~/.claude/AGENTS.md` 「용어·설명」 항목의 상세. 사용자가 답변을 읽고 **"그게 뭔데?" 라고 되묻지 않게** 하는 것이 목표다.

## 왜 이 문서가 있는가

답변이 어려운 진짜 이유는 단어가 어려워서가 아니라 **이름이 모호하거나 도중에 바뀌기 때문** 이다.

- ✗ "DB A 를 B 로 전환합니다" — A/B 가 뭐였는지, 무엇을 전환하는지 매번 위로 되짚어야 한다.
- ✓ "쓰기 대상을 기존 DB 에서 신규 DB 로 바꿉니다" — 이름만 읽고 바로 이해된다.

이름을 잘 고르면 **설명을 덧붙이지 않아도 되므로 답변이 오히려 짧아진다.**

## 규칙

### 1. 역할이 드러나는 이름을 쓴다

의미 없는 라벨(A/B, 1번/2번, 왼쪽/오른쪽, 이거/저거) 금지. 이름 안에 역할이나 상태가 들어가야 한다.

| 상황 | 쓰지 말 것 | 쓸 것 |
|---|---|---|
| 이중 쓰기의 두 DB | DB A / DB B | 기존 DB / 신규 DB (또는 primary / secondary) |
| 마이그레이션 전후 | 1번 / 2번 | 이전 스키마 / 새 스키마 |
| 복제 구성 | 서버 하나 / 서버 둘 | 원본 / 사본 |
| 배포 환경 | 서버 A / 서버 B | 개발 서버 / 운영 서버 |

고유명사가 이미 있으면 그대로 쓴다 (`imweb-dev`, `orders_v2`). 지어낸 별칭보다 실제 이름이 낫다.

### 2. 한 대상 = 한 이름, 끝까지 유지

- 한 번 "신규 DB" 라고 불렀으면 그 대화가 끝날 때까지 "신규 DB". `B`, `새 쪽`, `타깃`, `그것` 으로 갈아타지 않는다.
- **사용자가 이미 쓴 이름이 있으면 무조건 그 이름에 맞춘다.** 더 정확한 용어를 알아도 사용자 표현을 우선한다.
- 부득이 바꿔야 하면 `이제부터 X 를 Y 로 부르겠습니다` 한 줄을 남기고 바꾼다.

### 3. 범용 동사는 목적어 없이 쓰지 않는다

전환 / 처리 / 반영 / 적용 / 변경 / 정리 — 혼자 쓰면 무엇이 어떻게 되는지 알 수 없다.

- ✗ "primary 전환 시에는 다운타임이 없습니다"
- ✓ "쓰기 대상을 기존 DB → 신규 DB 로 바꿀 때는 서비스 중단이 없습니다"

형식: **`무엇을` + `어디서 → 어디로` + 동사**

### 4. 대상이 2개 이상이면 이름표부터 정하고 시작

계획·설명 본문을 쓰기 전에 한 줄로 선언한다.

> 이 작업에서는 지금 쓰는 DB 를 **기존 DB**, 새로 붙일 DB 를 **신규 DB** 로 부릅니다.

이후 본문에서는 설명 없이 그 이름만 쓴다. 매번 풀어 쓰지 않아도 되므로 전체 길이가 줄어든다.

### 5. 어려운 용어는 처음 한 번만 괄호로

- 한 답변 안에서 **처음 나올 때만** 괄호로 6~10자 설명. 두 번째부터는 용어만 쓴다.
- 예: "이중 쓰기(두 DB 에 동시에 저장) 로 구성하면…" → 이후엔 그냥 "이중 쓰기".
- 영문 약어는 처음에 한글 뜻을 붙인다: "DI(의존성 주입 — 필요한 객체를 대신 넣어주는 것)".
- **사용자가 먼저 쓴 용어는 설명하지 않는다.** 이미 아는 말이다.

### 6. 쉽게 쓰되 길이를 늘리지 않는다

- 괄호 설명은 용어당 1회.
- 비유는 필요할 때만, 한 문장 이내.
- 같은 내용을 쉬운 말로 다시 반복하지 않는다. 어려운 문장을 **덧붙이지 말고 바꿔 쓴다.**

### 7. 문제·리스크 설명은 "지금 → 바뀐 것 → 문제 → 영향 → 대책" 순서로

코드 분석 결과를 보고할 때 파일 경로·라인·식별자·수식(N~2N, ceil(N/5)) 을 앞세우면 사용자가 "그래서 뭐가 문제냐" 를 되묻는다.
(2026-09-02 post-msa 세션에서 지적 — 같은 내용을 아래 순서로 다시 쓰자 바로 통했다.)

1. **지금 일어나는 일** — 현재 동작을 사용자 관점의 한 장면으로 ("관리자가 공지 설정을 누르면 …")
2. **이 변경이 추가한 일** — 무엇을 왜 하게 됐는지
3. **문제** — 한 문장. 필요하면 비유 한 줄
4. **실제 영향** — 깨지는 것 / 안 깨지는 것을 나눠서. 수치는 수식 대신 구체 예시 하나 ("글 100개면 조회 100번")
5. **고치는 방법** — 범위와 크기까지

- 파일 경로·라인·함수명은 본문에서 빼고, 사용자가 코드를 열어야 할 때만 하나 정도 남긴다.
- 우려 항목 중 이미 다른 조사로 해소된 것은 "해소됨" 으로 한 줄 처리해 본론과 섞지 않는다.

## 보내기 전 점검

- [ ] 같은 대상을 두 가지 이름으로 부른 곳이 있는가
- [ ] A/B · 1번/2번 같은 의미 없는 라벨이 남아 있는가
- [ ] 목적어 없는 "전환 / 처리 / 반영" 이 있는가
- [ ] 처음 나온 전문용어에 짧은 설명이 붙었는가 (그리고 두 번 이상 반복하진 않았는가)
- [ ] 문제 보고가 "지금 → 바뀐 것 → 문제 → 영향 → 대책" 순서인가, 파일 경로·수식이 본문을 차지하고 있진 않은가
