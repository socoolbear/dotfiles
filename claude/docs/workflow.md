# 워크플로우 상세 가이드

> `~/.claude/AGENTS.md` 의 워크플로우 항목별 상세. 해당 상황에 진입하면 이 문서를 먼저 참조할 것.

## 1. 기본은 계획 모드

- 사소하지 않은 모든 작업은 계획 모드로 시작 (3단계 이상이거나 구조적 결정이 필요한 경우)
- 뭔가 잘못되면 즉시 멈추고 다시 계획 세우기 — 그냥 밀어붙이지 말 것
- 계획 모드는 개발할 때만이 아니라 검증 단계에서도 활용
- 모호함을 줄이려면 처음부터 상세 스펙을 작성할 것

## 2. 규모가 큰 계획은 적대적 검증을 거친 뒤 제출

### 수행 조건

아래 중 **하나라도** 해당하면 수행한다. 사용자가 따로 요청하지 않아도 수행한다.

- 변경 파일 3개 이상
- 구조적 결정 포함 (인터페이스 · 데이터 흐름 · 의존 방향이 바뀜)
- 되돌리기 어려움 (마이그레이션, 삭제, 외부로 나가는 작업)

어느 것도 해당하지 않으면 검증 섹션에 `해당 없음 — <사유 한 줄>` 로 기록하고 넘어간다.
"작아 보여서" 는 사유가 아니다. **위 세 조건 중 무엇에 걸리지 않는지**를 쓴다.

> 최신 모델은 시키지 않아도 자기 작업을 검증한다. 이 게이트는 사후 재확인이 아니라
> **실행 전 설계 오류를 잡기 위한 것**이므로, 규모가 작으면 비용만 든다.

### 순서

```
계획서 초안 작성 → 적대적 검증 → 지적사항 반영 → ExitPlanMode (사용자에게 진행 여부 질의)
```

`ExitPlanMode` 는 `claude/scripts/enforce-plan-review.sh` 훅으로 차단되며,
계획서에 `적대적 검증` **헤딩** (`## ` 로 시작하는 줄) 이 있어야 통과한다.
본문에서 언급만 해서는 통과하지 않는다. 훅은 무한 차단을 막기 위해
계획서당 1회만 차단하므로, **훅이 통과시켜 줬다는 사실이 검증을 생략해도 된다는 뜻은 아니다.**

### 검증 주체

`Agent` 도구로 **별도 리뷰어 서브에이전트** 를 띄운다 (`subagent_type: general-purpose`).
자기가 쓴 계획을 스스로 검토하면 감싸는 편향이 남으므로 인라인 셀프 리뷰로 대체하지 않는다.

**인원**: 기본 1명. **구조적 결정을 포함하거나 되돌리기 어려우면** 관점을 나눠 2~3명을 병렬로 띄운다.
파일 수만 많고 변경이 기계적이면 1명으로 충분하다.

리뷰어에게 넘길 것: 계획서 전문, 사용자의 원 요청 원문, 변경 대상 파일 경로.
부여할 역할: **"승인하지 말고 반박하라"** — 동의할 근거가 아니라 반증을 찾게 한다.

### 리뷰 관점 (전부 답하게 할 것)

| 관점 | 물어볼 것 |
|---|---|
| 요청 해석 | 원 요청을 잘못 읽었거나 범위를 임의로 넓힌/좁힌 지점은? |
| 회귀 | 빠진 케이스는? 이 변경으로 깨질 기존 동작은? |
| 과설계 | 더 단순한 대안이 있는 부분은? 굳이 안 건드려도 되는 파일은? |
| 검증 허점 | 이 계획의 검증 절차대로 하면 **무엇이 증명되지 않는가**? |
| 등급 | 각 지적을 `BLOCKER` (진행 불가) / `MINOR` (보완 권고) 로 분류 |

`BLOCKER` 는 계획서를 고쳐 반드시 해소한다. `MINOR` 는 반영하거나, 반영하지 않을 이유를 남긴다.

### 계획서에 남길 섹션

검증이 끝나면 계획서 맨 아래에 아래 섹션을 추가한다 (훅 통과 조건).

```markdown
## 적대적 검증
- 리뷰어: <에이전트 수 / 라운드 수>
- 지적 → 조치: <항목별로 반영 내용 또는 미반영 사유>
- 남은 리스크: <있으면 명시, 없으면 "없음">
```

## 3. 서브에이전트 위임 기준

모델 세대·계열마다 위임 성향이 반대로 갈린다 (어떤 모델은 과하게 위임하고, 어떤 모델은 더 쓰라고 권고된다).
그래서 "많이 써라 / 아껴 써라" 로 정하지 않고 **언제 위임하는지**로 정한다.

**위임한다**
- 독립적이고 병렬 가능한 큰 작업 (넓은 범위의 조사, 축이 갈리는 분석)
- 메인 컨텍스트에 담기 곤란한 양을 훑어야 할 때
- 별도 시점이 필요한 검증 — 계획 단계의 적대적 검증 (§2)

**위임하지 않는다**
- 직접 몇 번의 도구 호출로 끝나는 일
- 이미 끝낸 자기 작업을 다시 확인하는 일 (최신 모델은 시키지 않아도 한다)

**개수**: 하나로 끝나면 하나만. 서브에이전트 하나당 하나의 작업 — 집중 실행을 위해.
병렬 축이 실제로 갈릴 때만 늘린다.

**상비 위임 대상** (팀 모드 여부와 무관): 스코프 확정된 코딩은 `impl-dev`,
테스트·빌드·E2E 실행은 `qa-runner`, 검색·조사는 내장 `Explore`.
기준과 제약은 `@docs/team-mode.md` §5 참조.

## 4. 완료 전 반드시 검증

- 작동한다는 걸 증명하기 전까지 절대 작업 완료로 표시하지 말 것
- 필요한 경우 main 과 변경 사항 간의 동작 차이를 비교
- 스스로에게 물어볼 것: "시니어 엔지니어가 이걸 승인할까?"
- 테스트 실행, 로그 확인, 정확성 입증

## 5. 우아함을 추구할 것 (균형 있게)

- 사소하지 않은 변경이라면: 잠깐 멈추고 "더 우아한 방법이 있지 않을까?" 자문
- 수정이 어설프게 느껴진다면: "지금 내가 아는 모든 걸 바탕으로, 우아한 해결책을 구현해"
- 단순하고 명백한 수정엔 이 과정을 생략 — 오버엔지니어링 금지
- 결과물을 내놓기 전에 스스로 검토

## 6. 자율적인 버그 수정

- 버그 리포트를 받으면: 그냥 고칠 것. 하나하나 물어보지 말 것
- 로그, 에러, 실패한 테스트를 직접 찾아서 해결
- 사용자가 컨텍스트를 전환할 필요가 없도록
- 어떻게 하라는 말 없이도 실패한 CI 테스트를 직접 가서 고칠 것

## 작업 관리

1. **계획 먼저**: 빌트인 태스크 도구 (`TaskCreate`) 로 작업 항목 생성
2. **계획 검토**: 구현 시작 전에 `TaskList` 로 확인
3. **진행 상황 추적**: `TaskUpdate` 로 상태 변경 (in_progress → completed)
4. **변경 사항 설명**: 각 단계마다 상위 수준 요약 제공
5. **교훈 기록**: 수정 후 `@docs/feedback-loop.md` 의 라우팅 표에 따라 기록
