# 워크플로우 상세 가이드

> `~/.dotfiles/claude/CLAUDE.md` 의 워크플로우 항목별 상세. 해당 상황에 진입하면 이 문서를 먼저 참조할 것.

## 1. 기본은 계획 모드

- 방향이 갈리거나, 구조적 결정 (§2 정의 — 인터페이스 · 데이터 흐름 · 의존 방향이 바뀜) 이 있거나, 되돌리기 어려운 작업은 계획 모드로 시작 (구조적 결정의 범위는 2026-11-17 사용자 결정). 방향이 정해진 작업은 §7 의 사전 질문만 거치고 바로 진행 (2026-10-09 사용자 결정)
- 접근이 틀렸다는 게 드러나면 그냥 밀어붙이지 말고 계획을 다시 세운다 (방향이 바뀌면 §1 첫 줄·§2 조건을 다시 따지고, 되돌릴 수 있는 선택은 §7 결정 위임대로 진행한다)
- 계획 모드는 개발할 때만이 아니라 검증 단계에서도 활용
- **작업 분할은 착수할 때 정한다** (2026-11-17 사용자 요청). 범위를 훑은 뒤 (계획 모드면 계획서에) 단일 세션 / 서브에이전트 / 팀 / 자식 세션 중 무엇으로 할지 근거 한 줄을 남긴다. 기준 `@docs/team-mode.md` §1·§1-1. 작업 중에는 새 repo·작업 흐름이 생겼을 때, 흐름마다 사용자 결정이 따로 생겼을 때, 컨텍스트 경고가 떴을 때 다시 따진다
- 모호함을 줄이려면 처음부터 상세 스펙을 작성할 것

## 2. 규모가 큰 계획은 적대적 검증을 거친 뒤 제출

### 수행 조건

아래 중 **하나라도** 해당하면 수행한다. 사용자가 따로 요청하지 않아도 수행한다. 변경 파일 수는 조건이 아니다 (2026-10-09 사용자 결정).

- 구조적 결정 포함 (인터페이스 · 데이터 흐름 · 의존 방향이 바뀜)
- 되돌리기 어려움 (마이그레이션, 삭제, 외부로 나가는 작업)

어느 것도 해당하지 않으면 검증 섹션에 `해당 없음 — <사유 한 줄>` 로 기록하고 넘어간다.
"작아 보여서" 는 사유가 아니다. **위 두 조건 중 무엇에 걸리지 않는지**를 쓴다.

> 최신 모델은 시키지 않아도 자기 작업을 검증한다. 이 게이트는 사후 재확인이 아니라
> **실행 전 설계 오류를 잡기 위한 것**이므로, 규모가 작으면 비용만 든다.

### 순서

```
계획서 초안 작성 → 적대적 검증 → 지적사항 반영 → ExitPlanMode (사용자에게 진행 여부 질의)
```

`ExitPlanMode` 는 `claude/scripts/enforce-plan-review.sh` 훅으로 차단되며,
계획서에 `적대적 검증` **헤딩** (`## ` 로 시작하는 줄) 이 있어야 통과한다.
본문에서 언급만 해서는 통과하지 않는다. 훅은 무한 차단을 막기 위해
계획서당 1회만 차단하므로, **훅이 통과시켜 줬다는 사실이 검증을 생략해도 된다는 뜻은 아니다.**

### 검증 주체

`Agent` 도구로 **별도 리뷰어 서브에이전트** 를 띄운다 (`subagent_type: general-purpose`).
자기가 쓴 계획을 스스로 검토하면 감싸는 편향이 남으므로 인라인 셀프 리뷰로 대체하지 않는다.

**인원**: 기본 1명. **구조적 결정을 포함하거나 되돌리기 어려우면** 관점을 나눠 2~3명을 병렬로 띄운다.

리뷰어에게 넘길 것: 계획서 전문, 사용자의 원 요청 원문, 변경 대상 파일 경로.
부여할 역할: **"승인하지 말고 반박하라"** — 동의할 근거가 아니라 반증을 찾게 한다.

### 리뷰 관점 (전부 답하게 할 것)

| 관점 | 물어볼 것 |
|---|---|
| 요청 해석 | 원 요청을 잘못 읽었거나 범위를 임의로 넓힌/좁힌 지점은? |
| 회귀 | 빠진 케이스는? 이 변경으로 깨질 기존 동작은? |
| 과설계 | 더 단순한 대안이 있는 부분은? 굳이 안 건드려도 되는 파일은? |
| 검증 허점 | 이 계획의 검증 절차대로 하면 **무엇이 증명되지 않는가**? |
| 등급 | 각 지적을 `BLOCKER` (진행 불가) / `MINOR` (보완 권고) 로 분류 |

`BLOCKER` 는 계획서를 고쳐 반드시 해소한다. `MINOR` 는 반영하거나, 반영하지 않을 이유를 남긴다.

### 계획서에 남길 섹션

검증이 끝나면 계획서 맨 아래에 아래 섹션을 추가한다 (훅 통과 조건).

```markdown
## 적대적 검증
- 리뷰어: <에이전트 수 / 라운드 수>
- 지적 → 조치: <항목별로 반영 내용 또는 미반영 사유>
- 남은 리스크: <있으면 명시, 없으면 "없음">
```

## 3. 서브에이전트 위임 기준

모델 세대·계열마다 위임 성향이 반대로 갈린다 (어떤 모델은 과하게 위임하고, 어떤 모델은 더 쓰라고 권고된다).
그래서 "많이 써라 / 아껴 써라" 로 정하지 않고 **언제 위임하는지**로 정한다.
기본 모델 Fable 5.2 는 프롬프트가 위임을 권하면 쉽게 위임하고, effort 가 xhigh 이상이면 자기 작업 검토에도 서브에이전트를 띄운다.
서브에이전트는 세션 비용의 큰 몫이 될 수 있으니 아래 조건에 맞을 때만 띄운다 (2026-11-17 Anthropic Fable 5.2 프롬프팅 가이드).

### 3-1. 위임하는 경우 — 기본은 직접 구현

**팀 모드와 무관하다.** 혼자 도는 세션에서도 그대로 적용한다.
기본은 메인 루프가 직접 구현한다. 넘기면 맥락이 프롬프트와 요약을 거치며 빠지고, 모델 루프가 겹쳐 느려진다.
아래처럼 **새 컨텍스트가 실제로 필요할 때만** 위임한다 (2026-10-25 사용자 결정 — 서브에이전트를 단일 루프로 접으라는 Anthropic 글 반영).

**프로젝트 전용 에이전트가 우선한다.** 아래 표는 전역 폴백이다. 해당 작업을 다루는 프로젝트 에이전트 (`.claude/agents/`) 가 있으면 그쪽을 스폰하고, `impl-dev`·`qa-runner` 는 프로젝트에 대응 에이전트가 없을 때만 쓴다.

| 조건 | 위임 대상 |
|---|---|
| 파일이 겹치지 않는 독립 구현을 병렬로 돌릴 때, 또는 대량 반복 (마이그레이션·일괄 치환) | `impl-dev` (sonnet) |
| 출력이 길어 메인 컨텍스트를 채우는 테스트·린트·빌드·E2E (짧은 실행은 직접) | `qa-runner` (sonnet, 읽기 전용 + Bash) |
| 넓은 범위 검색·조사 | 내장 `Explore` + `model: sonnet` (새 정의 만들지 않음) |

**구현 위임 절차**

1. 파일 스코프와 구현 방향을 먼저 확정한다 (계획 모드 산출물이 있으면 그대로 쓴다).
2. `Agent` 도구로 `subagent_type: impl-dev` 스폰. 프롬프트에 반드시 담을 것:
   - 수정 대상 파일 **절대경로** 목록 + "스코프 밖 파일 수정 금지"
   - 구현 방향 — 무엇을 어떻게. "알아서 해줘" 금지
   - 따라야 할 기존 관용구 또는 참고 파일 경로
   - 검증 명령 (있으면) 과 커밋 금지 여부
3. 결과를 받으면 **내가 직접 diff 를 확인**한다. 완료 판단은 위임하지 않는다 (§4).

안전 불변식 (멱등성 · 정합성 · 롤백) 이 걸린 구현은 병렬이 가능해도 직접 한다.

**실패 시**: 같은 태스크에서 2회 실패하면 재위임하지 말고 직접 한다.
**팀 모드일 때의 추가 제약**: `@docs/team-mode.md` §5.

### 3-2. 병렬은 도구 호출 묶음이 기본

기본 병렬은 **한 메시지에 독립적인 도구 호출을 묶는 것**이다 (여러 파일 Read, 서로 무관한 검색, 독립적인 Bash).
앞 결과가 다음 호출의 인자를 정하는 경우만 순차로 둔다. 결과를 같은 컨텍스트에서 바로 보므로 단계 사이를 연결할 수 있다.

- 서브에이전트 병렬은 **축마다 새 컨텍스트가 필요할 때만** 쓴다 (축별로 대량을 훑거나 서로 다른 관점이 필요할 때).
  그때는 한 메시지에 동시 스폰한다. 하나 던지고 결과를 기다렸다가 다음을 던지는 건 낭비다.
- 쓰기 작업은 **파일 소유권이 겹치지 않게** 자른다. 겹치거나 일괄 치환처럼 충돌이 불가피하면
  `isolation: "worktree"` 를 준다.
- 못 자르면 억지로 나누지 않는다 — 소유권이 겹친 병렬 쓰기는 병렬이 아니라 충돌이다.

**순차로 둘 것**: 앞 단계의 산출물이 뒤 단계의 입력인 경우. 구현 → 검증 (§4) 이 대표적이다.
스코프·방향이 안 정해진 상태에서 인원부터 늘리는 것도 병렬이 아니다 — 먼저 §3-1 의 1단계를 끝낸다.

### 3-3. 그 밖의 위임

**위임한다**
- 독립적이고 병렬 가능한 큰 작업 (넓은 범위의 조사, 축이 갈리는 분석)
- 메인 컨텍스트에 담기 곤란한 양을 훑어야 할 때
- 별도 시점이 필요한 검증 — 계획 단계의 적대적 검증 (§2)

**위임하지 않는다**
- 직접 몇 번의 도구 호출로 끝나는 일
- 이미 끝낸 자기 작업을 다시 확인하는 일 (최신 모델은 시키지 않아도 한다)

**개수**: 서브에이전트 하나당 하나의 작업 — 집중 실행을 위해.
축이 실제로 갈리면 축마다 하나씩 **동시에** 띄운다 (§3-2). 축이 하나면 하나만 쓴다.

## 4. 완료 전 반드시 검증

- 작동을 증명하기 전에는 완료로 표시하지 않는다 — 테스트 실행, 로그 확인으로 입증
- 필요하면 main 과 변경 후의 동작 차이를 비교
- 배포가 끝나면 묻지 않고 직접 QA 한다 — 방법과 묻는 경우는 `deploy.md` §5 (2026-11-18 사용자 지시)

## 5. 우아함을 추구할 것 (균형 있게)

- 사소하지 않은 변경이라면: 잠깐 멈추고 "더 우아한 방법이 있지 않을까?" 자문
- 단순하고 명백한 수정엔 이 과정을 생략 — 오버엔지니어링 금지

## 6. 자율적인 버그 수정

- 버그 리포트를 받으면: 그냥 고칠 것. 하나하나 물어보지 말 것
- 로그, 에러, 실패한 테스트를 직접 찾아서 해결
- 사용자가 컨텍스트를 전환할 필요가 없도록
- 어떻게 하라는 말 없이도 실패한 CI 테스트를 직접 가서 고칠 것

## 7. 사용자 확인은 미리 모아 한 번에 묻는다 (선례 기반 추천과 함께)

> 작업 도중 하나씩 물으면 그때마다 작업이 멈추고 병렬로 돌릴 수 없다. 물을 것을 앞에 모아 한 번에 해소한 뒤 끝까지 몰아서 진행한다 (2026-10-06 사용자 지시).

### 언제

- **작업 착수 전** (계획 모드라면 계획서를 쓰기 전): 범위를 훑은 뒤 이번 작업에서 사용자가 정해야 할 것을 **전부** 뽑는다
  - 확인: 전제·범위·대상 해석이 맞는지
  - 결정: 설계 선택지, 트레이드오프
  - 요청: 사용자의 몸이 있어야 하는 일 (1Password 잠금 해제·휴대폰 승인·외부 팀 문의 발송 등). 로그인·OTP·관리자 화면 확인은 직접 한다 (아래 「꼭 묻는 목록」 4번)
  - 제안: 하면 좋을 추가 작업이나 다른 방향
  - 승인: 나중에 필요한 운영 배포·외부 발송 — 미리 받아 둘 수 있으면 같이 묻는다. 커밋·push·PR·dev 배포는 묻지 않는다 (`AGENTS.md` 「배포 확인 지점」)
- **작업 중 새 질문이 생기면**: 바로 묻지 말고 그 질문과 무관한 작업을 먼저 끝까지 진행한 뒤, 그 사이 쌓인 질문을 모아 한 번에 묻는다. 막혀서 더 진행할 게 없을 때만 즉시 묻는다

### 어떻게

- **`AskUserQuestion` 을 쓴다.** 한 번에 최대 4문항이므로 넘치면 중요한 순서로 나눠 연달아 묻는다
- **선택지 전에 선례부터 조사한다.** 같은 코드베이스의 기존 구현이 같은 문제를 어떻게 처리했는지 확인한다. 조사는 질문들끼리 독립적이면 병렬로 (서브에이전트 동시 스폰)
- 선택지마다 «어디서 이미 이렇게 하는지 (파일·선례)» 를 `description` 에 적고, 추천안은 첫 번째에 `(추천)` 을 붙인다. 선례와 다르게 가자고 추천할 때는 그 이유를 적는다
- 선례 조사 없이 일반론으로 만든 선택지를 바로 질문하지 않는다
- **묻지 않을 것을 먼저 걸러낸다.** 질문을 앞에 모으는 것이지 늘리는 것이 아니다. 아래 「꼭 묻는 목록」 에 없는 것은 묻지 않는다 — 관례상 답이 정해진 것, 코드·문서·명령으로 직접 확인할 수 있는 사실, 되돌릴 수 있는 선택이 모두 여기 든다. 이런 것은 질문과 같은 메시지에 «이렇게 가정하고 진행합니다» 로 한 줄씩 밝혀 두고, 이의가 있으면 고치게 한다 (2026-10-09 사용자 결정)
- 답을 받으면 결정을 기록(태스크 notes 등)하고, 서로 독립적인 후속 작업은 §3-2 대로 병렬로 띄운다

### 결정 위임 · 질문 대기열 (2026-11-17 사용자 요청)

> 근거: 대형 태스크 하나의 14일 동안 질문 229건 중 225건에 추천안이 있었다. 실행 승인 37건, 선례로 답이 나오는 기술 선택 93건, 반복 약 19건은 멈출 필요가 없었다.
> `ask-precheck.sh` hook 이 세션의 첫 `AskUserQuestion` 을 한 번 막고 「꼭 묻는 목록」 을 보여주며, 실행 승인 질문 (커밋 · push · PR · dev 배포) 은 매번 막는다. 글 질문은 `stop-gate.sh` (Stop 훅) 가 본다 — 지금은 기록만 하고, `~/.local/state/claude-loop/stop-gate/mode` 에 `block` 을 쓰면 한 번 막는다. 꼬리표 「사용자 몫」 의 분류 표시 없는 항목은 모드와 무관하게 한 번 막는다 (아래 「사용자 몫에 적기 전에」). 개입 수는 `loop-metrics.sh` 로 본다 (질문 창 · 글 질문 · 승인 입력 · 상태 묻기).

- **꼭 묻는 목록에 없으면 묻지 않는다** (2026-11-18 사용자 결정) — 아래 「꼭 묻는 목록」 에 드는 것만 사용자에게 묻는다. 나머지는 추천안을 스스로 정해 진행하고, 진행 문서 「결정 로그」 에 `[위임]` 으로 남겨 단계가 끝날 때 묶어서 보고한다. 사용자가 뒤집으면 고친다
- **질문 창뿐 아니라 답변 끝의 글 질문도 같다** — "~할까요?" · "원하시면 ~하겠습니다" · "말씀해 주시면 ~" 으로 턴을 끝내는 것도 질문이다. 목록에 없는 일이면 그렇게 끝내지 말고 진행한다. 조사 이어가기 · 초안·체크리스트 만들기 · Jira 상태 변경 · 커밋 · push · PR · dev 배포 · 운영이 아닌 병합이 여기 든다 (`AGENTS.md` 「배포 확인 지점」). 태스크 기록 repo (taskspace 워크스페이스의 notes.md · INDEX.md) 도 같다 — 상태가 바뀐 직후 · 보고 직전 · 세션을 닫기 전에 이 세션이 바꾼 경로만 커밋하고 push 한다. "지시가 있을 때만 커밋" 이라며 `[예외]` 로 남기지 않는다 (2026-11-18 사용자 지시)
- **묻기 전에 찾는다** — 진행 문서 「결정 로그」, `DECISIONS`, 태스크 notes 를 grep 한다. 답이 있으면 따르고 근거를 한 줄 남긴다
- **범위가 늘어나는 제안은 대기열로** — 목록에는 없지만 요청 범위를 넘거나 되돌리는 데 반나절 넘게 드는 제안은 스스로 진행하지 않는다. 「질문 대기열」 에 추천안과 함께 적고 원래 일을 계속한다
- **목록에 들어도 막히지 않으면 대기열로** — 다른 일을 할 수 있으면, 태스크 notes.md 「질문 대기열」 에 `질문 / 추천안 / 근거 / 상태: 대기` 로 적고 계속 진행한다. 묻는 때는 단계 경계나 막혔을 때다. 아침 요약 (`claude-loop brief`) 이 대기열을 모아 보여준다
- **한 주제는 한 번에** — 같은 주제를 여러 질문으로 나눠 연달아 묻지 않는다
- **답은 바로 기록한다** — 받은 답을 그 자리에서 「결정 로그」 에 적는다. 세션이 바뀌어도 같은 질문이 다시 나가지 않게 한다

#### 꼭 묻는 목록

> 근거 (2026-11-18 집계): 14일 동안 세션이 멈춘 2,298턴 중 792턴이 글 질문이었고, 그 답의 40% 가 "응" · "진행해줘" 뿐이었다. 위임하는 것을 나열하던 방식은 목록에 없는 일을 전부 묻게 만들었다.

1. **운영에 닿는 동작** — `AGENTS.md` 「배포 확인 지점」 그대로
2. **되돌릴 수 없는 것** — 데이터 · 브랜치 · 리소스 삭제, force push, 실제 돈이 움직이는 동작
3. **사용자 이름으로 다른 사람에게 나가는 글** — Slack 게시, Jira · PR 댓글. 초안 작성 · Jira 상태 변경 · 내 PR 의 제목·설명 수정은 묻지 않는다 (§9)
4. **사용자의 몸이 있어야 하는 일** — 1Password 잠금 해제 (Touch ID · 마스터 비밀번호), 휴대폰 푸시 승인 · 패스키 · CAPTCHA, 1Password 에 없는 계정. 남에게 권한을 요청하는 일은 요청 글 초안까지 만들고 3번을 따른다
5. **구조적 결정** — 인터페이스 · 데이터 흐름 · 의존 방향이 바뀌는 것 (§1, 2026-11-17 사용자 결정)
6. **선례가 없거나 서로 충돌하는 제품 · 정책 · 범위 결정**, 다른 사람의 결정을 뒤집는 일
7. **한도 · 예외를 쓰는 일** (우회 승인 등), 보안 경계를 낮추는 일

**로그인 · OTP 는 직접 한다** (2026-11-18 사용자 결정). 4번에 들지 않는 로그인 · OTP 입력 · 세션 만료 뒤 재로그인은 aside 의 1Password 확장으로 직접 한다.

- 1Password 에 있는 계정은 전부 쓴다. 그 사이트에 맞는 항목이 있으면 묻지 않고 로그인한다
- 같은 사이트에 항목이 여러 개면 (운영 · 테스트, 개인 · 회사) 진행 문서 · notes 에 적힌 계정을 고른다. 적힌 게 없으면 직전에 쓰던 계정을 고르고 「결정 로그」 에 남긴다. 맞는 항목이 없으면 다른 항목으로 돌려 쓰지 않고 4번으로 넘긴다
- 로그인은 수단이지 승인이 아니다. 운영 화면에 로그인했어도 그 안의 운영 동작은 1번을 따른다
- 비밀번호 · OTP 값을 파일 · 로그 · 메시지에 남기지 않는다. 로그인이 안 된다고 `.env` · 셸 기록 · 설정 파일에서 토큰 · 비밀번호를 찾아 돌려 쓰지 않는다
- 야간 모드에서는 야간 가드가 aside 를 확인창에서 멈춘다. 이 규칙은 낮 세션에만 적용된다

#### 사용자 몫에 적기 전에 (2026-11-18 사용자 지적)

> 상태 꼬리표의 「사용자 몫」 도 질문이다. 글 질문을 막자 질문이 이 줄로 옮겨 갔다. `stop-gate.sh` 가 분류 표시 없는 항목을 한 번 막는다.

항목마다 아래 순서로 걸러내고, 남은 것만 적는다.

1. **QA · 확인은 직접 한다** — "한 번 써 보기" · "화면 확인" 을 넘기지 않는다. 배포했으면 쓰는 사람의 경로로 직접 써 본다 (aside 브라우저 · 실제 호출 · 로그). 수단이 없거나 보안 · 고위험 동작일 때만 남긴다 (`AGENTS.md` 「배포 확인 지점」)
2. **찾아볼 수 있는 사실 · 수단은 찾는다** — "~가 있는지" · "어떻게 확인할지" 는 질문이 아니라 조사 거리다. 코드 · DB · 로그 · 관리 화면 · 문서를 먼저 찾고, 못 찾았을 때만 찾아본 곳과 함께 남긴다
3. **선택지 · 제안을 통째로 넘기지 않는다** — "그대로 둘지, 고칠지, 되돌릴지" · "~도 맞출지 결정" 대신 추천안을 스스로 고르고, 꼭 묻는 목록에 닿기 직전까지 진행한다. 리뷰 지적이 타당하면 후속 PR 을 올리고 운영 병합 승인만 남긴다. 요청 범위를 넘는 제안은 「질문 대기열」 에 적고 사용자 몫에는 쓰지 않는다
4. **답 없이 할 수 있는 「다음」 이 있으면 끝내지 않는다** — 초안 작성 · 조사 · 검증을 "정해 주시면 ~" 뒤로 미루지 않는다

남은 항목은 `[분류] 승인 · 결정할 것 하나 — 추천안` 으로 쓴다. 분류는 「꼭 묻는 목록」 번호 순서대로 `[운영]` `[복구불가]` `[외부글]` `[본인]` `[구조]` `[정책]` `[예외]` 다. 어느 분류에도 들지 않으면 물을 일이 아니다.

```
✗ **사용자 몫** ① 지적 2건을 그대로 둘지, 후속 PR 로 고칠지, revert 할지 ② 운영 전송 본문을 볼 방법이 있는지
✓ **사용자 몫** [운영] 지적 2건을 고친 후속 PR 의 main 병합 승인 — 추천: 병합 (운영 전송은 로그에서 확인함)

✗ **사용자 몫** DM 에서 한 번 써 보기 / 스킬도 같은 방식으로 맞출지 결정
✓ **사용자 몫** 없음   ← 직접 써 봤고, 스킬 맞추기는 질문 대기열에 추천안과 함께 적음
```

#### 그 밖의 규칙

- **고객·외부 팀에 물을 목록도 질문만 나열하지 않는다.** 항목마다 데이터·코드로 먼저 유추하고 «추천안 + 근거» 를 붙여, 상대가 "맞다/아니다" 로만 답하면 되게 만든다. 데이터로 확인되는 부분은 확인해 질문에서 빼고, 유추와 확인된 사실은 구분해 적는다 (2026-11-11 사용자 지적 — 고객 확인 항목을 질문만으로 나열)

## 8. 태스크 세션은 현재 tmux 세션의 window 로 연다

> 태스크(taskspace `tasks/<ID>/` 등) 를 처리할 Claude 세션을 새로 띄울 때는 **지금 내가 도는 tmux 세션에 window(탭) 를 추가**한다. 새 tmux 세션·새 Ghostty 창(`open -na Ghostty`) 으로 띄우지 않는다 — 창이 흩어져 사용자가 다시 모아야 한다 (2026-11-02 사용자 지시).

```bash
cmd="STATUSLINE_LINK_URL=<원문 링크> CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude -n task-<ID> --dangerously-skip-permissions $(printf %q "<첫 지시>"); exec zsh"
command tmux new-window -d -t "$(command tmux display -p '#{session_name}'):" -n "task-<ID>" -c "<태스크 디렉토리>" "${cmd}"
```

- 첫 지시나 브리프에 진행 문서의 「결정 로그」 경로를 넣는다. 새 세션이 이미 정한 것을 다시 묻지 않게 하려는 것이다 (§7)
- `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 을 직접 붙인다 — `cct` 는 zsh 함수라 이 명령에서 쓰지 않고, 빼면 그 세션은 팀 기능이 꺼진다
- `STATUSLINE_LINK_URL` 은 태스크의 원문 링크 (Jira 이슈·Slack 쓰레드 등) 를 status line 에 Cmd+클릭 링크로 띄운다 (`~/.dotfiles/claude/scripts/statusline-command.sh`). 원문 링크가 없으면 이 `변수=값` 을 뺀다. 환경변수라 실행 중인 세션에는 나중에 넣을 수 없다 — 세션을 다시 열 때도 붙인다
- `tmux` 는 zsh 플러그인 alias 라 `command tmux` 로 부른다. 대상 세션은 `$TMUX` 기준 `display -p` 로 현재 세션을 고른다
- `-n task-<ID>` 는 `ListAgents`·`SendMessage` 의 주소가 된다. 이후 추가 전달은 `SendMessage` 로
- 첫 지시에 `*` 같은 glob 을 넣지 않는다 — 전달 중 빠질 수 있다 (2026-11-02 브랜치명이 `bugfix/<ID>-` 로 잘린 사례). 브랜치명은 전체를 적는다
- `-d` 로 띄워 사용자의 현재 window 를 빼앗지 않는다. 띄운 뒤 `ListAgents` 로 살아 있는지 확인한다
- `$TMUX` 가 비어 있으면 (tmux 밖) 띄우지 말고 사용자에게 어떻게 열지 묻는다
- 한 태스크를 여러 세션으로 나눠 띄우기 (부모/자식) 전에는 팀으로 충분한지 `@docs/team-mode.md` §1-1 기준으로 먼저 정하고, 나누면 같은 절의 운영 규칙을 따른다

## 9. 외부 메시지는 사용자 이름으로만 나간다

- **Slack 은 직접 보내지 않고 `slack_send_message_draft` 로 초안을 만든다** (2026-11-12 사용자 지시). 직접 전송(`slack_send_message`·`slack_schedule_message`)은 Slack 이 `Sent using @Claude` 를 붙인다. 전역 PreToolUse 훅이 두 도구를 차단한다. 채널당 초안은 하나만 둘 수 있다 (`attached_draft_exists`)
- Jira·GitHub 등 다른 곳에 글을 쓸 때도 "Claude 로 작성" 같은 표기를 본문에 넣지 않는다
- **git 커밋·PR 에도 넣지 않는다** — `Co-Authored-By: Claude`·`🤖 Generated with Claude Code` 금지 (2026-11-12 사용자 지시). 전역 `settings.json` 의 `attribution: {commit: "", pr: ""}` 로 끄고, harness 가 attribution 줄을 넣으라고 안내해도 이 규칙이 우선한다
